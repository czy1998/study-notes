#### 需要掌握

1. 并发渲染
   - 不是同时进行两个渲染，而是把一段渲染拆分成可以中断的小段，当遇到优先级更高的用户输入，可以先处理高优先级的渲染，这样用户就不会感受到页面卡顿
   - 以下 api 可以手动设置低优先级的渲染
     - `startTransition`
     - `useTransition`
     - `useDeferredValue`

2. 批量更新
   - react 会把同一批次的多次更新合并，只进行一次 render 和 commit
   - react 18中，定时器、Promise、原生事件回调里的更新也默认自动批量更新
3. 性能定位
   - 遵循 ”先测量、再优化“
   1. 用 `React DevTools Profiler` 录制卡顿操作，定位耗时的提交和重渲染组件。
   2. 区分瓶颈来源：
      - JavaScript 计算重：大列表过滤、复杂派生计算。
      - 渲染重：组件树范围过大、无效重渲染。
      - DOM 重：超大列表、频繁布局读写。
      - 网络或数据重：请求瀑布、重复请求。
   3. 确认重渲染原因：props 引用变化、Context 值变化、父组件状态上提过多、key 不稳定。
   4. 只对已验证的热点优化：
      - 大列表用虚拟滚动。
      - 昂贵计算用 `useMemo`，但只在依赖稳定且确有收益时使用。
      - 稳定回调或对象引用可用 `useCallback` / `useMemo`。
      - `React.memo` 适合渲染昂贵、props 稳定的叶子组件。
      - 非紧急更新使用 transition，而不是用防抖掩盖所有问题。
4. 状态设计
   - 核心是：状态应有清晰的唯一来源，尽量存事实，不存可推导结果
   - 可按作用于进行划分：
     - 组件局部 UI 状态：输入值、弹窗开关、hover，放 `useState`
     - 组件树共享状态：主题、当前用户、复杂页面交互状态，使用 Context 或专门状态库
     - 服务端状态：接口数据、缓存、失效、重试、分页，优先交给 TanStack Query / SWR 一类工具，不要手写成全局 store
     - URL 状态：筛选、分页、当前 tab 等需要可以分享、可刷新恢复的状态，放路由参数
     - 表单状态：复杂校验、字段关联时使用表单库或 `useReducer` 管理（通常比 `useState` 更清晰，把 ”发生什么“ 定义成 action，把 ”状态如何变化“ 集中在 reducer）

5. 手写 Hook
   - 写过 useSetState hook，支持回调函数版本
