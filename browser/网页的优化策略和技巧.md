# 网页的优化策略和技巧

## 一、加载性能优化（让页面更快地呈现在用户面前）

1.  优化图片
    图片通常是页面上体积最大的资源。
    - 选择合适格式：优先用 WebP（体积比 JPEG/PNG 小 25%-35%），兼容性不好的地方降级成 JPEG。
    - 压缩图片：用 imagemin、tinypng 这类工具在构建时自动压缩。Umi 项目可以配置 `image-webpack-loader`。
    - 响应式图片：用 `srcset` 属性，为不同屏幕尺寸提供不同分辨率的图片。在用户中心这类后台系统里，图片主要就是头像，通常用固定尺寸就行，不太需要这个。

2.  使用 CDN（内容分发网络）
    把 `react`、`antd` 这类体积大、版本又比较稳定的第三方库，通过 CDN 方式引入。好处有两个：
    - 用户访问其他网站时可能已经缓存过这些资源，这里可以直接命中缓存，省掉一次下载。
    - 减少自己服务器的带宽压力。

    在 Umi 里可以通过 `externals` 配置，把 React、ReactDOM、Ant Design 排除在打包之外，然后在 `index.html` 里用 `<script>` 标签引入 CDN 地址。

3.  懒加载和预加载
    - 图片懒加载：页面上不可见的图片先不加载，等用户滚动到可视区域再加载。用户中心的用户列表里，头像就是一种场景。可以直接用 `<img loading="lazy">` 属性，浏览器原生支持。
    - 路由懒加载：Umi 默认就是按路由拆分代码的。用户只访问 `/login` 时，永远不会加载 `/admin` 这个页面对应的 JS。这能显著减少首屏需要下载的资源。
    - 预加载关键资源：用 `<link rel="preload">` 提前加载字体、首屏 CSS 这类关键资源。Umi 的 Prefetch 机制也会在空闲时，悄悄
      预加载其他页面的 JS，让用户在跳转时直接命中缓存，体验很流畅。

4.  压缩与合并文件
    - 压缩 JS / CSS：`npm run build` 的时候，底层的 Webpack 会用 Terser 插件压缩 JS、用 css-minimizer 压缩 CSS，去掉注释、空格，变量名混淆等等。
    - 合并文件：Webpack 会把多个小模块合并成一个个 chunk，减少 HTTP 请求次数。HTTP/2 普及之后，多路复用可以同时传输多个文件，合并的需求不像以前那么强烈了，但对老协议仍然有意义。

5.  利用浏览器缓存
    部署时，打包出来的 JS 和 CSS 文件名里都带有 content hash（比如 `login.a1b2c3.js`）。
    - 只要文件内容没变，hash 就不变，文件名就不变。我们对这类文件配置一个超长的 `Cache-Control: max-age=31536000`，浏览器就直接走本地缓存，根本不再发请求。
    - 如果文件内容变了，hash 会跟着变，文件名也就变了，浏览器会把它当成一个新资源去下载。这样就做到了“缓存不失效、更新不遗漏”。

    在用户中心的 Nginx 部署里，可以这样配：

    ```nginx
    location /static/ {
    expires 1y;
    add_header Cache-Control "public, immutable";
    }
    ```

6.  代码分割（Code Splitting）
    Umi 默认支持基于路由的自动分割，还可以手动用 `import()` 做更细粒度的拆分。

    比如一个大型图表库只在统计页用得到，就可以写成：

    ```js
    const Chart = React.lazy(() => import("./Chart"));
    ```

    这样首页根本不会加载这个库的代码。

7.  使用异步加载 JavaScript
    对于非关键的第三方脚本，比如统计埋点、客服组件等等，可以用 `<script async>` 或 `<script defer>` 标签。它们不会阻塞页面解析。
    - `async`：下载完立刻执行，执行顺序不保证。
    - `defer`：等 HTML 解析完之后按顺序执行。

8.  选择轻量级框架和库
    Ant Design Pro 本身就已经做了一定的“瘦身”。项目搭建完之后，那些用不到的模板页面、Mock 数据、多余的语言包等等，都可以删掉，减少最终打包体积。你笔记里记录的“前端初始化 → 框架介绍 / 瘦身”这一步，其实就是这个优化思路的体现。

### 二、渲染性能优化（让页面交互更流畅）

1. 减少重排（Reflow）和重绘（Repaint）

   DOM 结构改变或样式改变时，浏览器会重新计算布局和重新绘制像素。频繁触发会很消耗性能。
   - 批量操作 DOM：用 `document.createDocumentFragment` 一次性插入多个节点，而不是循环里多次插入。
   - 用 CSS 动画替代 JavaScript 动画：CSS 动画在合成线程上执行，不会阻塞主线程；JS 动画在主线程跑，如果主线程忙着算布局，就会掉帧。
   - 避免频繁读写样式属性：一条读紧接着一条写，会导致浏览器强制同步布局。

2. 使用虚拟 DOM（React 特性）

   React 的 Virtual DOM 天然就是一种渲染优化。当数据变化时，它先生成一棵新的虚拟 DOM 树，和旧的 Virtual DOM 做 Diff 比较，再只把差异部分更新到真实 DOM。这大大减少了实际的重排重绘次数，用户中心表格频繁更新这种场景下优势很明显。

3. 减少不必要的组件重渲染

   这是项目里可以主动优化的重点，用 Hooks 来处理：
   - `useMemo`：缓存一个复杂的计算结果，依赖项不变就直接返回旧值，不重新算。
   - `useCallback`：缓存函数引用。比如把回调函数传给子组件时，引用不变就可以配合 React.memo，让子组件不需要跟着父组件一起重新渲染。
   - `React.memo`：让纯展示型组件只在 props 变化时才更新。
     在用户管理表格这种数据量大的场景里，这些优化很有用：筛选条件的计算结果可以 `useMemo`，传给表格子组件的回调可以 `useCallback`。

4. 使用 key 属性优化列表渲染

   React 用 `key` 来判断列表里的元素是新增、删除还是移动的。

   一定要用唯一、稳定的标识，比如用户的 `id`。不要用数组的 `index`。因为当列表顺序变的时候，index 也会跟着变，React 可能会把整个列表都重新渲染一遍，而不是仅移动那些真正变了的几项，这会浪费大量性能。

### 三、性能监控与分析工具

优化不能靠猜测，得有数据支撑。

`Google PageSpeed Insights / Lighthouse`：输入网址就能拿到性能评分和优化建议。
`Chrome DevTools Performance 面板`：录制一段用户操作，分析哪些环节耗时最长。
`Web Vitals`：核心网页指标，比如 LCP（最大内容绘制）、FID（首次输入延迟）、CLS（累计布局偏移）。
持续监控这些指标，才能有针对性地优化，而不是盲目地做。

总结来说，用户中心项目在加载性能方面，主要靠 Umi 的自动分包 + CDN 引入大库 + Nginx 强缓存 这一套组合；在渲染性能方面，主要是依赖 React Virtual DOM 的先天优势 + useMemo/useCallback 的精细控制。两者的结合让整个应用的首屏速度和交互体验都有保障。
